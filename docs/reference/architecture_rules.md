# アーキテクチャルール

## レイヤー責務

1. **入口層**は Discord イベントまたは HTTP リクエストを受け、入力検証、認証状態確認、応答形式の変換を行います。
2. **サービス層**は AI、画像生成、認証、ユーザー解決などのユースケースを実行します。外部 API とトランザクションの境界はここで管理します。
3. **モデル層**は DB のテーブル、関連、制約を表現します。外部サービス呼び出しや画面表示の都合を持ち込まないようにします。
4. **設定・共有基盤**は環境依存値と共通初期化を提供し、入口層から直接秘密情報を組み立てないようにします。

## 依存と初期化

- Bot は `setup_hook` で DB、AI、生成、ログ、画像サービスを構築してから Cog を登録します。
- Web はアプリファクトリで設定・DB・Blueprint を登録し、モジュール import 時の重い初期化を避けます。
- DB セッションはコンテキスト管理し、成功時に commit、失敗時に rollback、終了時に close します。
- スキーマ変更は Alembic のバージョン履歴で管理し、モデルだけを変更して DB と不一致にしません。

## データ整合性

- ユーザー外部アカウントは provider と provider_user_id で一意に解決します。
- ユーザーへの Bot プロファイル割り当て、Bot プロファイル、グループ、ペルソナの有効状態を確認してから利用します。
- 生成画像はアプリ内ユーザーへ関連付け、Web ではセッションユーザーの画像だけを返します。
- 外部ファイル保存と DB 保存の失敗を記録し、再処理可能な状態を維持します。

## セキュリティ境界

- OAuth2 の state をセッションに保存し、コールバックで検証します。
- リダイレクト先ホストは許可リストで検証します。
- 秘密鍵、API トークン、OAuth2 シークレットは環境変数または既存のシークレット基盤から取得し、ログへ出力しません。
- 画像配信は設定された生成画像ディレクトリを起点にし、ユーザー認可が必要な画面のデータ取得ではセッション ID を条件に含めます。

## 文書と実装の差異

上記は現行実装から抽出したルールと、維持すべき設計方針です。`FLASK_SECRET_KEY` の本番必須化、ペルソナディレクトリ変数名の統一、ファイルと DB の整合性回復処理は未確定であり、設計変更として決定してから実装してください。
